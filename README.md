# OrphanVM

**Live update with CPU preservation support**

OrphanVM aims to achieve sub-100ms Virtual Machine downtime during a full Host
OS replacement. Designed for host environments running Linux kernel 7.2 or later (Linux 7.2+),
it achieves "Pauseless Update" by allowing VMs to continue executing instructions on their assigned
physical cores throughout the next host kernel boot phase. This is accomplished by "orphaning" the
VM—decoupling its active execution from the host kernel and handing it off to a specialized
bare-metal component called the **Caretaker**.

For an in-depth dive into the architecture and mechanisms (like the Caretaker
and KVM ABI), please see the design document at `docs/DESIGN.md`.

## Directory Structure

- **`buildroot/`**: The Buildroot system for generating the root
  filesystems (initramfs) and toolchains for both the host and guest
environments.
- **`overlays/buildroot_guest/`**: Custom overlay files injected into the guest
  Buildroot system (e.g., the `autologin` script).
- **`overlays/buildroot_host/`**: Custom overlay files injected into the host
  Buildroot system (this automatically dynamically bundles the guest kernel and
initramfs inside the host).
- **`docs/`**: Project documentation, including the primary architectural
  design (`DESIGN.md`).
- **`linux/`**: The Linux kernel source code, containing the modifications
  required to support OrphanVM capabilities.
- **`nanovmm/`**: Source code for NanoVMM (nvmm), the minimalistic Virtual
  Machine Monitor used to launch and orchestrate the orphaned guest
  environments.

## Getting Started

### 1. Clone the Repository

Clone the repository and ensure you pull down the necessary git submodules
(`linux` and `buildroot`):

```bash
git clone --recursive git@github.com:soleen/orphanvm.git orphanvm
cd orphanvm
```

*(Note: If you forgot `--recursive`, the `Makefile` is configured to
automatically fetch and initialize missing submodules during the build
process.)*

### 2. Simulator Setup (Optional)

If you plan to run the host kernel in a simulator, you should install Intel
Simics. It is recommended to install it into a dedicated `simics/` directory
within the workspace. *(Note: The public release of Intel Simics only provides
x86 and RISC-V targets; simulating the `aarch64` build requires an
internal/commercial Simics license with ARM packages).*

First, navigate to the [Intel Simics Simulator Public
Release](https://www.intel.com/content/www/us/en/developer/articles/tool/simics-simulator.html)
page to get your unique download links.

*Note: The URLs below contain a `<unique_id>` that is auto-generated by Intel's
portal. Replace them with the actual links provided on the download page.*

1. Create the `simics/pkgs` directory and download the installation packages into it:

```bash
mkdir -p simics/pkgs
cd simics/pkgs

# Download the Intel Simics Package Manager into simics/pkgs/
wget https://registrationcenter-download.intel.com/akdlm/IRC_NAS/<unique_id>/intel-simics-package-manager-1.18.0-linux64.tar.gz

# Download the Simics Package Bundle into simics/pkgs/
wget https://registrationcenter-download.intel.com/akdlm/IRC_NAS/<unique_id>/simics-7-packages-2026-18-linux64.ispm

# Extract the package manager
tar xf intel-simics-package-manager-1.18.0-linux64.tar.gz
cd ../..
```

2. Install the packages into `simics/install`:

```bash
./simics/pkgs/intel-simics-package-manager-1.18.0/ispm packages \
    --install-bundle ./simics/pkgs/simics-7-packages-2026-18-linux64.ispm \
    --install-dir ./simics/install \
    --non-interactive
```

3. Initialize the Simics project in `simics/`:

```bash
SIMICS_PYTHON=$(which python3) ./simics/install/simics-7.84.0/bin/project-setup ./simics --ignore-existing-files --no-venv
```

Your Simics workspace is now fully initialized at `simics/`, providing the `./simics` binary and associated tooling.

### 3. Build the Project

A single Makefile coordinates the building of the Linux kernel, the Buildroot
initramfs, and the NanoVMM binary. By default, it builds for the `x86_64`
architecture.

To build everything for the default `x86_64` architecture, simply run:

```bash
make
```

To build for the `aarch64` (ARM64) architecture, set the `ARCH` variable:

```bash
ARCH=aarch64 make
```

This will:
- Merge the base `configs/<arch>/linux_*_config_fragment` files with the
  kernel's default configuration and compile the `bzImage` (or `Image` for
  ARM64) for both the host and the guest.
- Configure Buildroot using the `configs/<arch>/buildroot_*_config_fragment`
  files and build the root filesystems. The host initramfs will be automatically
  packaged with the guest artifacts.
- Compile the `nanovmm/nvmm` binary and prepare the execution scripts in
  `output_<arch>/bin/`.

### 4. Environment & Execution Setup

#### Shell Environment Setup (`env.sh`)
Before running OrphanVM tools, source the `env.sh` script in your shell to automatically add `output_<arch>/bin` to your `$PATH`:

```bash
# Default to x86_64 on x86 hosts (or arm64 on aarch64/arm64 hosts)
source env.sh

# Or explicitly specify the target architecture
source env.sh arm64
```

Once sourced, commands such as `ovm_simics`, `ovm_console`, `ovm_guest`, `ovm_test`, and `nvmm` can be executed directly from any directory.

### 5. Run the VM

The project utilizes two different platforms to provide full hardware
virtualization emulation depending on the target architecture:
- **Intel Simics:** Used to emulate Intel hardware virtualization extensions
  (VMX/VT-x).
- **QEMU:** Used to emulate AMD hardware virtualization extensions (SVM) and
  ARM64 hardware virtualization extensions (EL2).

#### For **Intel x86_64**:
You must run the host environment in the high-fidelity Intel Simics simulator,
as it provides the required VMX emulation.

```bash
ovm_simics
```
Simics provides cycle-accurate simulation and hardware-level debugging (see
Section 6). The serial console is exposed via `telnet localhost 4000`.

**Connecting to Serial Console (`ovm_console`):**
To connect to the Simics serial console without terminal output spam while Simics is restarting or offline, use the auto-reconnecting helper script:

```bash
ovm_console
```
This script silently checks port 4000 and automatically connects `telnet` as soon as Simics opens the port.

**Connecting via SSH (`ovm_ssh`):**
The host system runs systemd with `systemd-networkd` auto-configuring network interface `eth0` via DHCP. Simics NAPT port forwarding maps host port `2222` to port `22` (Dropbear SSH daemon) on the simulated host. You can SSH directly into the host OS using the shortcut script:

```bash
ovm_ssh
```

Alternatively, connect directly via OpenSSH:
```bash
ssh -p 2222 root@localhost
```

#### For **AMD x86_64 and ARM64**:
These platforms are supported via QEMU emulation with TCG acceleration, which
fully emulates their respective hardware virtualization extensions.

**AMD x86_64 / ARM64:**
```bash
ovm_qemu [ovm_guest|ovm_guest_qemu|none] [-c <cpus>]
```

`ovm_qemu` and `ovm_simics` accept an optional parameter controlling which guest VM auto-starts inside the host:
- `ovm_guest` (default): auto-starts guest VM using NanoVMM.
- `ovm_guest_qemu`: auto-starts guest VM using QEMU with `/dev/kvm`.
- `none`: boots host VM without starting any guest VM.

The QEMU instances are configured with nested virtualization extensions enabled
(SVM for x86, EL2 for ARM64) to allow `/dev/kvm` to function inside the host.
The serial console is connected directly to your current terminal.

#### Running the Guest VM
Once you are logged into the host environment (regardless of the architecture or
simulator/emulator used), you can launch the virtual machine using either NanoVMM or QEMU:

1. **Option A: Launch via NanoVMM (`nvmm`)**
   ```bash
   ovm_guest
   ```
2. **Option B: Launch via QEMU (with `/dev/kvm` Hardware Acceleration)**
   ```bash
   ovm_guest_qemu
   ```

Both scripts automatically locate the bundled guest kernel and initramfs, booting the guest VM with 1GB memory, 1 vCPU, `kexec-tools` available in `/usr/sbin/kexec`, and serial console output automatically routed to `ttyS0` for x86 or `ttyAMA0` for ARM64.

#### Runtime Guest Control via FIFO
When NanoVMM is running, runtime control commands can be written directly to its non-blocking FIFO (default path: `/tmp/nvmm_<session>.fifo`):

```bash
# 1. Suspend and preserve VM state via LUO (default: all target pCPUs if orphan mode, and all vCPUs)
echo "suspend" > /tmp/nvmm_orphanvm_session.fifo

# 2. Suspend with explicit strategy:
# - Preserve specific host pCPUs (vCPUs default to all):
echo "suspend cpu1" > /tmp/nvmm_orphanvm_session.fifo
echo "suspend cpu1,cpu2" > /tmp/nvmm_orphanvm_session.fifo
echo "suspend cpu1-3" > /tmp/nvmm_orphanvm_session.fifo

# - Preserve all vCPUs without preserving host pCPUs:
echo "suspend vcpu" > /tmp/nvmm_orphanvm_session.fifo

# - Preserve specific pCPUs and explicit vCPUs:
echo "suspend cpu1,vcpu0,vcpu1" > /tmp/nvmm_orphanvm_session.fifo
echo "suspend cpu1-2,vcpu0-1" > /tmp/nvmm_orphanvm_session.fifo

# 3. Cancel preservation and resume guest VM execution:
echo "resume" > /tmp/nvmm_orphanvm_session.fifo

# 4. Cleanly terminate guest VM:
echo "quit" > /tmp/nvmm_orphanvm_session.fifo
```

**Strategy Validation Rules:**
- **vCPU Completeness Constraint**: If vCPUs are explicitly specified (`vcpuX` or `vcpuX-Y`), **ALL guest vCPUs must be listed** (e.g. `vcpu0,vcpu1` for a 2-vCPU VM). Partial vCPU lists are rejected with an error to prevent invalid or corrupted VM resume state.
- **pCPU Flexibility**: Physical host CPUs do **not** have to be all specified (preserving any subset of pCPUs or none is allowed).
- **Default vCPU Inclusion**: If no vCPU tokens are explicitly specified (e.g. `suspend cpu1`), all guest vCPUs are preserved by default.

## 5. Debugging with Intel Simics

Simics provides powerful capabilities for hardware-level debugging and tracing.
For example, if you want to inspect the exact moment a `vmexit` occurs, you can
catch it directly within the host Linux KVM module without modifying any source
code.

### Method 1: Source-Level Debugging with GDB

Because the Simics installation includes the `simics-gdb` package, you can
attach a standard GDB instance directly to the simulated CPU. This allows you to
step through KVM and KVM Kexec code.

1. First, inside your simulated Linux host, locate the exact memory address of
the VM Exit handler (e.g., `vmx_vmexit`):
   ```bash
   cat /proc/kallsyms | grep vmexit
   ```
   *Example output: `ffffffff82c8f8f0 T vmx_vmexit`*

2. Pause Simics by pressing `Ctrl+C` in the terminal where Simics is running.
3. Start the GDB server attached to the primary CPU:
   ```text
   simics> new-gdb-remote cpu=qsp.mb.cpu0.core[0][0] port=9000
   simics> run
   ```
4. Open a new terminal on your host machine, launch GDB with your uncompressed
host kernel, and connect to the Simics instance:
   ```bash
   gdb output_x86_64/linux_host/vmlinux
   (gdb) target remote localhost:9000
   ```
5. Set a hardware breakpoint on the kernel's VM Exit handler. If your kernel was
compiled without debugging symbols, you can break directly on the absolute
address you found in step 1:
   ```bash
   (gdb) break *0xffffffff82c8f8f0
   (gdb) continue
   ```
When the guest triggers a `vmexit`, GDB will freeze the simulation, allowing you
to inspect registers, variables, and the call stack.

### Method 2: Address-Based Hardware Breakpoints

If you prefer to debug entirely within the `simics>` CLI without GDB, you can
set hardware execution breakpoints directly.

Using the same address found via `/proc/kallsyms` (e.g., `ffffffff82c8f8f0` for
`vmx_vmexit`), pause the simulation (`Ctrl+C`) and set an execution (`-x`)
breakpoint:
```text
simics> bp.memory.break -x address=0xffffffff82c8f8f0
simics> run
```

When the breakpoint is hit, the simulation will pause. You can use the following
Simics commands to inspect the state:
* `step-instruction` (`si`): Step forward exactly one CPU instruction.
* `print -x %rax`: Print the hexadecimal value of a register.
* `read-reg cr3`: Read specific control registers.
* `list-registers`: View all architectural registers, including hidden VMX state.
